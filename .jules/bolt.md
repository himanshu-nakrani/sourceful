## 2025-02-18 - [Optimize Correlated Subqueries with CTE Limit Pushdown]
**Learning:** The `list_conversations` endpoint had a performance regression because it evaluated a correlated subquery (`SELECT COUNT(*) FROM messages...`) for *every* conversation row matching the `WHERE` clause before sorting and applying `LIMIT 200`. For users with large histories, this scanned the entire conversation list. A `LEFT JOIN` + `GROUP BY` is an anti-pattern here because it forces a full table join before the limit.
**Action:** Always wrap the base paginated query in a Common Table Expression (CTE) to apply the `ORDER BY` and `LIMIT` first. Then, select from the CTE and apply the correlated subquery in the outer query. This forces the DB to evaluate the expensive subquery only `LIMIT` times.
